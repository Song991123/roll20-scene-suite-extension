# 배포 전 최적화 검증 보고서

작성일: 2026-08-29

비교 기준: `9eb10a50f348bd8b09e15ebed3a97cc627e2826e`

작업 브랜치: `codex/pre-release-optimization`

## 결론

현재 변경은 표시 순서와 연출 순서를 바꾸지 않는 범위에서 적용했다. 자동 회귀검사, 문법 검사, 출력 동등성 검사, 성능 측정은 모두 통과했다. Roll20 개발방에서는 00번과 10번의 서버 저장본이 로컬 파일과 SHA-256까지 같고 샌드박스가 오류 없이 시작되는 것을 확인했다.

03·05·07·08·09번의 최적화는 로컬 Roll20 모의 실행에서 동작과 호출 순서를 비교했지만, 현재 개발방에 해당 모듈이 설치되어 있지 않아 실제 맵 화면의 시각 검증은 이번 보고서에 포함하지 않는다. 따라서 이 브랜치는 배포 후보로 백업할 수 있지만, 기본 브랜치에 합치기 전 실제 사용 방의 복제본에서 컷인·스탠딩·대사창의 짧은 시각 확인을 한 번 더 하는 편이 안전하다.

## 작업 전 백업

- 작업 시작점과 원격 브랜치가 모두 `9eb10a50f348bd8b09e15ebed3a97cc627e2826e`인지 확인한 뒤 수정했다.
- 기존 `codex/sheet-helper-integration` 브랜치는 수정하지 않았다.
- 최적화는 별도 `codex/pre-release-optimization` 브랜치에서만 진행했다.

03번과 09번은 카드 이름이 다른 캐릭터 이름을 포함하는 기존 규칙을 보존해야 하므로 캐릭터와 카드의 이름 비교 자체는 `O(C×K)`로 남겼다. 이번에 줄인 것은 Roll20 저장소를 반복해서 전부 훑는 횟수다. 이름 매칭 방식을 더 줄이면 표시 대상과 순서가 달라질 수 있어 이번 범위에서는 건드리지 않았다.

## 측정 결과

측정값은 같은 PC에서 기준 커밋과 현재 작업 파일을 동일한 Roll20 모의 실행기에 넣은 중앙값이다. 실제 Roll20 서버 지연이 아니라 코드 자체와 Roll20 객체 API 호출량을 비교한 값이다.

| 대상 | 입력 크기 | 기준 | 최적화 후 | 변화 |
|---|---:|---:|---:|---:|
| 05 대사 줄바꿈 문자열 계산 | 10,000자 | 517.931 ms | 0.118 ms | 약 99.98% 감소 |
| 08 컷인 캡션 문자열 계산 | 10,000자 | 539.045 ms | 0.093 ms | 약 99.98% 감소 |
| 03 관리 갱신 | 1,000개 규모 | 2,353.559 ms | 625.302 ms | 73.4% 감소 |
| 09 관리 갱신 | 1,000개 규모 | 3,035.292 ms | 1,161.584 ms | 61.7% 감소 |
| 10 반복행 정렬 | 10,000행 | 138.385 ms | 32.134 ms | 76.8% 감소 |
| 10 인식 데이터 로딩 | 실제 5개 시트, 21회 중앙값 | 13.510 ms | 8.031 ms | 40.5% 감소 |

호출량 비교:

- 03, 1,000개 규모: `findObjs` 5,001회 → 3회, 검사 객체 25,010,001개 → 15,003개, 불필요한 `set` 1,000회 → 0회.
- 09, 1,000개 규모: `findObjs` 6,002회 → 3회, 검사 객체 30,022,004개 → 15,006개, 불필요한 `set` 1,001회 → 0회.
- 07: 캐릭터가 1,000명인 조건에서 캐릭터 조회 1,001회 → 1회, 동일값 `set` 1회 → 0회, 관계없는 매크로 이벤트 갱신 1회 → 0회.
- 10: 반복되는 선택 방식 직렬화는 527회 → 51회다. 복원된 배열과 객체는 기준판과 똑같이 1,375개 굴림별로 독립적이고 수정 가능해, 한 굴림의 변경이 다른 굴림에 번지지 않는다.

05와 08의 큰 감소율은 **문자열을 만드는 계산만** 잰 값이다. 실제 Roll20에서는 글자마다 실행되는 객체 `get`·`set`·`toFront`와 클라이언트 렌더 비용이 남아 있으므로, 이 수치를 전체 대사창 재생시간 감소율로 해석하지 않는다. 해당 API 호출 순서는 표시 순서 보존을 위해 바꾸지 않았다.

10개처럼 작은 입력에서는 새 조건 검사 비용 때문에 03·09가 일부 실행에서 0.1~1 ms 정도 느리게 측정되었다. 실제 Roll20 객체 조회와 쓰기 횟수는 이때도 크게 줄었고, 항목 수가 늘수록 개선 폭이 커진다. 작은 입력의 미세한 수치를 숨기지 않고 배포 판단에 포함했다.

## 정리한 개발 흔적

- README와 검증 문서에 남아 있던 사용자 PC 절대경로를 일반적인 예시 경로로 교체했다.
- 브라우저 배포에 필요 없는 시트 분석 도구를 `public/assets`에서 `tools`로 옮겼다. 빌드와 검사는 같은 파일을 계속 사용한다.
- 테스트용 `__benchmark`, `__optimizationTest`는 검사 도구가 메모리에서만 임시로 덧붙이며 `public/scripts`에는 들어가지 않는다.
- 원문 제공 페이지의 `sources.js`는 최종 코드에서 다시 생성했다.

안전 조건과 이벤트 필터가 추가되어 00~10 스크립트 자체는 약 0.3% 커졌다. 대신 실행 중 필요하지 않은 73,836-byte 시트 분석 도구를 `public`에서 `tools`로 옮겨 실제 배포물 전체는 줄었다. 원본 분석 도구를 삭제한 것이 아니라 빌드 도구 위치로 이동했다.

00~10을 난독화·최소화하는 압축은 적용하지 않았다. Roll20 편집기에 직접 붙여 넣는 배포 방식과 오류 줄 추적, 기존 주석 가독성을 보존하면서도 배포 총량이 줄어드는 안전한 정리만 채택했다.

개발방에는 이번 최적화 대상인 03·05·07·08·09가 설치되어 있지 않다. 자동 검사는 해당 모듈의 출력과 Roll20 API 호출 순서를 비교했지만, 맵 화면에서 실제로 컷인 위아래 관계를 보는 검증을 대신한다고 표현하지 않는다. 특히 03의 동일값 `set` 생략이 Roll20 클라이언트의 재렌더 부작용에 영향을 주지 않는지는 복제 방의 시각 확인 대상으로 남긴다.

## 최종 배포 전 남은 확인

1. 실제 사용 방을 복제한다.
2. 03·05·08·09를 현재 브랜치 버전으로 넣는다.
3. 스탠딩이 있는 상태에서 대사창과 컷인을 각각 한 번 실행한다.
4. 카드 토큰보다 컷인이 위에 있고, 대사·스크립트 패널 위치가 기존과 같은지 눈으로 확인한다.
5. 문제가 없으면 이 브랜치를 기본 브랜치에 합치고 기존 CI/CD를 실행한다.
